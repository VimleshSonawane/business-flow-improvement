# Real-data analysis — Boston 311, 2024

This replaces the simulated weekly numbers as the evidence base for this project.
The original simulated pipeline, its 12-week plan, and its stage times are NOT
presented as findings from this data. They remain only as the proposed
improvement framework in the other docs, clearly separated from the real analysis
below.

## Source

- City of Boston, Analyze Boston (data.boston.gov), dataset "311 Service Requests"
- Dataset id: 8048697b-ad64-4bfc-b090-ee00169f2323
- Resource used: "311 Service Requests - 2024", resource id dff4d804-5031-443a-8409-8344efd0e5c8
- Licence: Open Data Commons Public Domain Dedication and License (PDDL)
- Retrieved 2026-10-27 via the CKAN datastore API, with aggregate SQL queries
  (counts by subject, type, source, case status, and on_time).
- Total records in the 2024 resource: 306,756.

## What the data does and does not show

- It shows: open date, closed date, SLA target date, on_time flag, case status,
  subject/department, type, source channel, and neighbourhood.
- It does NOT show stage-by-stage waiting vs. working time. The dataset has no
  intake, scoping, quality, or delivery timestamps. So no stage waiting times
  are claimed from this data. Any stage split in this repo is a proposed
  measurement to add, not a measured result.
- Average open-to-close time was not verified in this round: the aggregate
  query for it was blocked by the portal (403) and is not reported here.
  The SLA measure below (on_time) is the verified time measure.
- Case status "Open" is the status in the extract, not a backlog count at
  31 December 2024. Do not present it as an end-of-year backlog.

## Headline findings, 2024

- Total requests: 306,756.
- Closed in the extract: 256,838 (83.7%). Still open in the extract: 49,918 (16.3%).
- SLA on time: 234,564 (76.5%). Overdue: 72,192 (23.5%).
- That headline hides a split. Routine, well-defined work is on time;
  enforcement and repair work is not.

## The real bottleneck: on-time rate by type

Full verified table in tools/tableau-311-2024-ontime.csv:

| Type | Volume | On time | Overdue |
|---|---:|---:|---:|
| Parking Enforcement | 63,112 | 48.2% | 32,704 |
| Request for Pothole Repair | 10,620 | 40.8% | 6,286 |
| Requests for Street Cleaning | 22,507 | 90.7% | 2,099 |
| Missed Trash/Recycling/Yard Waste/Bulk Item | 10,593 | 97.7% | 239 |
| Improper Storage of Trash (Barrels) | 20,460 | 99.4% | 121 |

Parking Enforcement alone is 45.3% of ALL overdue cases. Parking Enforcement
plus Pothole Repair together are 54.0% of all overdue cases, from only 24.0%
of total volume. That is the flow problem, in one sentence.

## Intake channels (source)

- Employee Generated: 129,573 (42.2%)
- Citizens Connect App: 79,749 (26.0%)
- Constituent Call: 54,474 (17.8%)
- City Worker App: 31,617 (10.3%)
- Self Service: 11,343 (3.7%)

Intake is not one channel. Almost half of requests are generated by employees
and city workers, not by residents. An intake fix that only improves the
resident app misses the largest intake source.

## What this changes in the project

The original simulated Pareto (incomplete intake, unclear owner, late quality,
excess WIP, last-minute changes) is replaced, for the evidence section, by
this real Pareto of overdue work:

1. Parking Enforcement overdue volume — triage, ownership, and SLA definition
   for enforcement cases need to be understood first, before any generic fix.
2. Pothole Repair overdue volume — same question, at smaller scale.
3. Everything else in the top 20 is mostly on time, so the lesson is not
   "the whole system is slow" — it is "two case types break the SLA".

The proposed improvement plan therefore starts with: measure stage times
for Parking Enforcement and Pothole Repair specifically, map their actual
handoff path, and only then set targets. No target (lead time, throughput,
rework) is claimed as achieved from this data, because this dataset is a
diagnostic snapshot, not a before-and-after trial.
